### 意图识别的边界

自然语言首先由本地规则解析器填充表单。OrcaRouter 的意图总结只用于给用户解释请求、提出澄清问题；当前实现不会把模型猜测写回地点、日期、人数等结构化字段。Chat Agent 在有资料时会检索本地原文，再让模型根据原文回答。报价比较与费用计算不交给模型。

## A/B/C/D 复杂度公式

当前定义在 `config/llm_tiers.json`，计算实现位于 `agents/intent_router.py`。每个特征先换算到 0–100 分：

```text
总分 = 输入长度 × 0.20
     + 已填出差字段长度 × 0.20
     + 出差字段覆盖率 × 0.15
     + 词汇复杂度启发值 × 0.20
     + 条件表达数量 × 0.25
```

具体算法：

- 输入长度：当前输入与最近最多 4 条历史消息的字符总数；达到 2,000 字符时该项为 100。
- 出差字段长度：8 个已知字段中非空值的字符总数；达到 800 字符时该项为 100。
- 字段覆盖率：上述 8 个字段中已填字段数除以 8。
- 词汇复杂度启发值：分词后“不同词元占比 × 60 + 长度至少 6 字符的词元占比 × 40”。中、日文按连续字符块切分，英文和数字按连续拉丁字母数字切分；这是可复现的文本启发值，不是语言学或模型自评。
- 条件表达数量：匹配代码中的日文、中文条件词，英文条件词（完整单词），以及日期和时间格式；每 7 个匹配项该项达到 100。匹配是规则近似，不能理解复杂逻辑关系。
- 加权总分使用 Python `round()` 取整。配置权重之和必须为 1.0，否则配置读取会报错。

| 档位 | 当前分数范围 | 配置路由 | 费用边界 |
|---|---:|---|---|
| A | 76–100 | `orcarouter/fusion` | 可能产生费用 |
| B | 51–75 | `orcarouter/fusion-mini` | 可能产生费用 |
| C | 26–50 | `orcarouter/auto` | 自动路由所选模型可能产生费用 |
| D | 0–25 | `orcarouter/free` | 免费路由；官方说明不会回退到付费模型 |

OrcaRouter 的 Auto Router 会按难度选择模型。免费模型以 `-free` 结尾；免费请求可能被拒绝。详见 [OrcaRouter Auto Router](https://docs.orcarouter.ai/routing/auto-router)、[免费模型说明](https://docs.orcarouter.ai/routing/free-models) 和 [模型目录](https://docs.orcarouter.ai/getting-started/models)。

**授权与费用记录：**本次 API 验证仅调用免费路由，没有调用 A/B 路由或可选付费模型。代码中的 A/B/C 映射尚未做实际模型调用验证；不能将“代码已配置路由”描述为“已验证模型能力”。如果应用运行环境配置了 Key，评分落入 A/B 时会请求对应路由，C 会请求 Auto Router；使用前需确认 OrcaRouter 工作区的计费设置。

## 真实数据 API 调查与当前接入状态

`config/providers.json` 中航班、铁路、酒店、地面交通、天气、日历、模型和邮件服务均标记为 `not_configured`。当前实现没有对酒店或铁路服务发起实时查询。

### 酒店

[楽天トラベル空室検索 API](https://webservice.rakuten.co.jp/documentation/vacant-hotel-search) 可以按区域、坐标、酒店 ID、入住日期、人数和价格等条件查询可预约房型及方案，响应包括设施地址、经纬度、最近车站和房间方案价格。该服务需要申请并配置应用凭据。响应中的 `reserveRecordCount` 是返回的预约候选记录数量，不能当作酒店剩余房间的实时库存数。当前项目没有该 API 凭据或适配器。

### 铁路和新干线

[駅すぱあと经路查询](https://docs.ekispert.com/v1/api/search/course/extreme.html) 可提供路线、时间和票价等信息，需要 API Key；其文档所列套餐及评估申请需要单独办理。查阅的经路与时刻文档未发现可返回新干线余席数量的字段。[JR 东海时刻表](https://railway.jr-central.co.jp/pwd/_pdf/N700S-every.pdf) 可作为运行时刻参考，但不能提供某个座位的实时余席和交易价格。

东京—新大阪的参考票价采用 [JR 东海 Tours 的新干线价格比较页面](https://travel.jr-central.co.jp/plan/tokushu/shinkansen/station/) 中普通车指定席通常期约 ¥14,720 作为一个模拟方案的基准。它是参考金额，不是实时查询或预订报价。Google Routes 的[公共交通路线文档](https://developers.google.com/maps/documentation/routes/transit-route)也已查阅；其路线票价属于估算，不能验证新干线库存，因此当前模拟实现没有把它冒充成预订接口。

## 模拟报价算法与限制

实现文件：`tools/simulation_provider.py`。这些值是确定性的比较样例，不使用随机数，也没有向酒店、铁路 API 发请求：

1. 按输入出发时间生成两套方案；第二套出发时间比第一套晚 10 分钟。
2. “速达方案”用 147 分钟作为单程模拟时长；“费用重视方案”用 180 分钟。往返按各自时长计算。出发、到达时刻是由用户输入时间加减时长生成的模拟时刻，不是列车时刻表查询结果。
3. 东京—大阪名称匹配时，第一套用 ¥14,720 作为普通车指定席参考基准；第二套固定少 ¥320，即 ¥14,400，作为人为设定的比较样例。其他区间分别用 ¥12,000 和 ¥10,800 的占位模拟值。各金额乘人数和往返 2 次，计算交通费。
4. 返回出发时刻按“回程截止时间减单程模拟时长”计算，并至少留出出发后到达再等 30 分钟的间隔。如果因此超过回程截止时间，后续本地行程校验会标为不满足条件。
5. 如需住宿，住宿晚数按出发日期与回程日期相差天数计算，至少按 1 晚；统一假设 1 间房。两档每晚分别固定为 ¥13,800 和 ¥10,800。酒店名称、所在地、步行分钟数（8/12 分钟）均为生成的虚构值。
6. 座位余数（8/14 席）、当地交通（¥1,200/¥900 每人）、日当（¥2,000 每人）都是演示用固定值；日当没有读取公司规程。住宿不按旅客人数推断房间数。
7. 模拟记录遵守项目的 `PlanInput` 报价结构，并明确 `data_kind=simulation` 和来源说明。确定性计算器负责汇总和比较费用、行程时间、条件问题。模拟数据不能预订、报销或证明真实有余席。

其中只有第一档东京—大阪交通费引用公开参考金额。其他时间、第二档价差、酒店和余席等是为了让 Agent 流程可运行的固定模拟假设；因此结果页面及计划书必须保留“模拟、不可预订”的标识。

## 内部运行追踪文件

开发诊断写入 `output/agent-traces/agent-trace.jsonl`，由 `agents/trace_log.py` 追加。文件不由 HTTP 路由提供，也不出现在用户页面或计划书中；路径已加入 `.gitignore`。每条记录包含时间、追踪 ID、阶段、处理方、状态、模型路由、档位分数与特征、数据类型、引用数量、检索方式和已识别的错误代码。

追踪器不保存 API Key、提示词、聊天正文、资料原文、收件人或完整行程字段。日志写入失败不会中断用户流程。每次聊天或申请请求使用新的追踪 ID；它记录单次请求的调用步骤，不会跨多个请求自动合并成同一条用户会话。

聊天记录可区分意图理解、资料检索和有依据的回答生成；申请记录可区分本地字段解析和意图理解；报价模拟、确定性计算和邮件草稿也会记录为本地步骤。免费路由返回 `err_free_access_denied` 时，聊天 Agent 会停止后续模型请求，避免继续重试；诊断错误代码只写本地内部日志，用户页面显示普通失败提示。
