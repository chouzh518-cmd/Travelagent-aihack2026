# 预选演示方案：出差旅费 Agent

本文供项目成员准备预选与路演，不是用户界面文案。竞赛没有提供预选规则或评分表，因此以下是按五个目标维度设计的产品证据，不代表评审方已确认的评分标准，也不承诺预选结果。

## 案例依据与解释边界

用户提供的截图作为案例参考。截图仅显示部分《旅費規程》，没有显示修订日期、适用公司、适用人员范围的完整上下文或第 6 条后续内容。演示中应称为“提供的规程截图摘录”，不可称为已经核实的参赛公司的正式有效规程。

截图可辨识内容：

- 第 3 条：旅费以本店所在地为基点，按一般最短路径计算；因业务需要、灾害或其他不得已理由绕行时，按实际经过路线计算。
- 第 4 条：旅费原则上在返回公司后计算支付；可预先领取概算款，返回后应尽快结算。
- 第 5 条：因业务需要、旅行状况或其他特别理由导致规定旅费不足时，可以支付超出部分的实际费用。
- 第 6 条：出差旅费包括交通费、住宿费和日当；截图中交通费按实际费用计算，住宿料写为每晚 10,000 日元。
- 日当的具体金额和计算条件没有出现在截图可见区域，不能补造。

“每晚 10,000 日元”是截图的规定金额。第 5 条同时列出特定原因下支付超出部分实际费用的可能性，所以不能把 10,000 日元简单实现为绝对硬上限，也不能把超额报销实现成自动批准。应展示标准金额、超额金额、原文依据和待确认的业务理由。

案例还需核对东京是否为规程所说的本店所在地。实际出发地为东京本身并不能证明东京就是计算基点。

## 演示案例

目标：根据客户的到达要求，为东京出发、前往大阪客户现场的国内出差整理计划。交通按规程实际费用结算；住宿以截图所示的每晚 10,000 日元为规定金额；超额费用只有在存在规程列明的业务或特别理由时才进入例外核验。

第一轮对话只给出东京、大阪和客户到达要求时，Agent 应先收集影响结果的缺失信息：出发日期与最早可出发时间、客户要求的具体到达时刻、人数、返回计划、是否需要住宿，以及东京是否为计算旅费的本店所在地。缺少这些条件时不生成分钟级行程或总价。

使用者上传截图后，系统先显示识别状态和原文预览；回答规程问题时引用条款编号与页码。识别不完整或日当内容缺失时，系统保留“未确认”，不按行业惯例填值。

## 路演流程建议

1. 展示自然语言任务及规程截图上传。
2. OrcaRouter 整理意图；Agent 识别缺少的出发时间、客户到达期限、人数和计算基点，向使用者提出必要问题。
3. Agent 检索并引用第 3、5、6 条，说明最短路径原则、实际费用和住宿规定金额；指出日当金额未显示。
4. 交通工具调用真实路线服务，按指定日期和到达时刻找可行路线。酒店工具按入住日期查询实时房价与可订房型。当前未接入的余席或价格不显示成真实数据。
5. Agent 校验到达期限、住宿标准和待核验的超额理由，生成计划书及未发送的审批邮件草稿。
6. 路演说明页展示一次已成功的工具调用记录、数据来源与更新时间，以及五个目标维度的证据。普通用户产品页只显示业务计划和必要的数据来源标记，不显示模型路由、密钥或内部调试信息。

若实际数据不满足要求，演示 Agent 应报告冲突并列出可调整条件；不得为完成演示而伪造“符合”结论。

## 五个目标维度的可见证据

| 维度 | 应由演示证明的行为 |
| --- | --- |
| セキュリティ | API 密钥只在后端；日志不记录密钥、完整聊天、上传原文或邮件收件人；上传资料按用途隔离；邮件只生成草稿，不代替用户发送或订票。 |
| コストパフォーマンス | 只用真实查询结果比较交通时间、费用与住宿金额；未确认日当不计入总额；说明标准金额与需理由的超额实费。 |
| 信頼性・堅牢性 | 每条路线、价格和酒店记录带来源及查询时间；区分时刻表、实时空房、参考价与模拟数据；格式校验失败或 API 无响应时停止错误结论并保留待确认项。 |
| 自律性 | 从对话和上传规程提取条件，调用交通/住宿工具，核对硬约束，处理条件冲突，再生成可审阅的计划书和邮件草稿。不可逆操作保留人工确认。 |
| アイデア・独創性 | 把规定旅费、按实际路线计算、超额费用理由与归社后精算连成一条可追溯业务流程；既优化行程，也说明哪些费用可计算、哪些需理由或原文确认。 |

## 真实数据接入现状与限制

- 交通：駅すぱあと API 有路线、运费和时刻相关接口。官方免费方案的路线搜索受限，只能使用平均等待时间探索，不能做精确时刻表探索；官方另提供 90 天免费评估版。严格验证客户到达时刻时，需要评估版或适用的时刻表权限和 API 密钥。参见 https://api-info.ekispert.com/plan/ 和 https://docs.ekispert.com/v1/api/search/course/extreme.html 。
- 住宿：楽天トラベル空室検索 API 文档说明可以查询实时可订房间，需要 `applicationId` 与 `accessKey`，并且要用地区代码 API 获取正式地区代码。返回的预约候选记录数不能解读成酒店总余席数。参见 https://webservice.rakuten.co.jp/documentation/vacant-hotel-search 和 https://webservice.rakuten.co.jp/documentation/get-area-class 。
- 座位库存：目前核对的路线搜索和住宿 API 不提供新干线座位库存字段；没有来源的余席数量不得展示。
- OrcaRouter：此前模型目录请求成功，但免费模型生成请求返回 `err_free_access_denied`。免费资格恢复并成功完成生成请求以前，不能说路演 Agent 已经由 OrcaRouter 完成意图理解。此前同意仅使用免费额度，不能切换到收费路由。
- 项目当前的交通、酒店模拟供应器仍会生成模拟报价。模拟结果只能演示系统流程，不能作为实时票价、房价、空房或审批合规证据。

## 完成预选演示前的阻断项

1. 恢复并实测 OrcaRouter 免费模型生成权限；保留仅免费路由的保护。
2. 申请駅すぱあと 90 天评估或确认能够返回指定日期的时刻表路线；免费平均等待时间方案不足以证明指定到达时刻。
3. 申请楽天 Web Service 凭据并通过地区代码 API 解析大阪的精确住宿区域；没有日期时不能查询真实空房。
4. 决定路演案例的出发日期、客户到达时刻、人数、返程计划、住宿与东京是否为本店所在地。
5. 将真实结果和模拟结果分开标记；对真实 API 保留脱敏请求/响应摘要、查询时间与来源，供评委核验。

## 当前实现

- 员工首页只有一个推进页面：选择公司登记项目、查看关联资料、上传补充文件、通过对话补充条件，然后在同一页生成计划书和审批依赖文模板。
- 项目目录目前以 data/projects/catalog.json 加 Markdown 文件模拟后台登记库。planty 是虚构演示项目；系统按登记的日文标签读取出发地、目的地、预算、期间、目的和其他字段。
- 点击生成计划书时，本地模拟供应器生成两种新干线相当方案，并将结果写入计划书。没有填写的日期、出发时间、到达期限、人数、住宿条件会使用显式标注的演示假设：下一日、08:00、12:00、20:00、1 人、无需住宿。此类默认值只服务于模擬流程，不能被理解成用户确认的出差条件。
- 模拟算法固定使用两种时长样例（往返各 147 分钟或 180 分钟）、出发偏移（0 或 10 分钟）、东京—大阪单程运费样例（¥14,720 或 ¥14,400）、每人当地交通样例（¥1,200 或 ¥900）。若模拟为需要住宿，则添加虚构酒店与每晚 ¥9,800 或 ¥12,000 的样例。归程从模拟的归着期限倒推，并为当天行程预留最少 30 分钟间隔。
- 模拟结果不含实时运转信息，酒店名称与位置是虚构数据，余席、预约可否、实际价格、日当金额及实际规程适用性保持未确认。¥30,000 的演示预算会用于比较已知模擬小计；该比较不能证明真实交通方案可行或规程合规。
- 公司尚未提供駅すぱあと路线 API 与楽天旅行业务 API 所需的项目凭据/权限，当前实现不向这两家服务发送请求。候选 API 能力与申请条件见上文。数据接口接通前，页面和计划书都会明确说明数值来自本地模擬。
- OrcaRouter 只在用户点击对话发送时参与意图理解和检索回答；本地路线/住宿模拟由固定规则生成。模型路由与步骤记录保存在内部运行追踪中，不显示在员工计划书界面。

本地模拟数据用于检验“读项目资料、补充条件、形成比较、暴露预算冲突、生成计划书”的流程。演示时要说明路线、费用与住宿均为模擬结果，并现场查看生成计划书中的模擬标记、未确认项和预算差额。
