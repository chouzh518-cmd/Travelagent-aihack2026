## 0. 一页了解项目现状

### 项目是什么

员工选择公司登记的差旅项目，上传差旅制度或项目文件，通过对话补充条件；系统展示项目条件、检索相关资料、模拟比较交通和住宿方案，再生成差旅计划书。用户可以继续补充信息，也可以生成一封可编辑、可复制的审批邮件草稿。

项目目标是把原本分散的资料阅读、条件确认、行程比较、规程检查和文书整理连成一个推进式流程。它面向“业务自动化 AI Agent”比赛，但目前仍是演示型原型，不是接入公司数据库和真实出行服务的生产系统。

## 1. 项目案例、来源和边界

### planty 演示项目

- 项目名：planty
- 出发地：东京
- 目的地：大阪府大阪市
- 预算上限：30,000 日元
- 期限：一天以内
- 目的：参考大阪市公开示范项目，与客户确认通信弱电场、远程监控、车路协同的导入条件
- 项目资料未填写：明确出发日期和时刻、客户要求到达时刻、返程期限、人数、住宿需求

planty 是虚构的演示项目。资料引用了大阪市公开示范项目背景，不表示 planty 与相关政府部门、交通机构、运营企业或客户有真实合作。公开项目介绍也不能证明具体客户地址、访问许可、会议时间、列车时刻、实际票价或座位库存。

### 差旅制度截图

用户提供了一张制度页面截图，项目组将可辨识部分转录到 data/projects/planty/travel_policy_excerpt.md。可辨识的内容包括：

- 第 3 条：以公司本店所在地为计算基点，原则上按一般最短路线计算；因业务或不可避免原因绕行时，按实际路线计算。
- 第 4 条：原则上回公司后计算支付，可预支概算款，回程后尽快结算。
- 第 5 条：业务、旅行状况或特别原因导致规定金额不足时，可支付超过部分的实际费用。
- 第 6 条：旅费含交通费、住宿费和日当；交通费按实费；住宿费写为每晚 10,000 日元。
- 截图可见范围没有日当金额、适用对象、审批流程和完整的超额住宿操作细节。

因此，项目只能展示“提供的制度截图摘录”和对应文字，不能称为已经确认有效的完整公司规程。第 5 条是例外支付依据，不表示超额费用会自动获批；东京是否为规程要求的本店所在地也尚未核实。

## 2. 用户一路提出并已落实到界面的产品要求

### 流程和内容

1. **以项目为起点**：先让员工选择已登记的差旅项目，例如 planty；项目资料应由公司预先维护，员工不用重复录入已有字段。
2. **资料优先，对话补充**：开始时允许上传差旅制度和项目相关文件；员工再用对话补充日期、希望到达时间、人数、目的等资料中没有的内容。
3. **删除中间页面**：把核心工作收敛到一个推进式页面，而不是把员工引导到多页工具入口。
4. **计划书生成后继续沟通**：计划书下方仍能返回对话，补充信息后重新生成计划书。
5. **邮件生成入口**：计划书旁有生成邮件入口；邮件使用 OrcaRouter 免费路由，模型不可用时显示“功能正在维护”并提供可填写模板，不把维护状态说成永久不可用。
6. **面向员工隐藏开发细节**：不向普通用户显示申请编号、模型档位、模型路由、API Key、内部追踪、资料库内部连接状态、无关的资料确认区块。
7. **计划书精简**：用户要求移除数据确认范围、资料来源清单、上传资料列表、对话补充记录及额外确认项等内部信息，让员工主要看到计划书本身。
8. **小问号操作提示**：说明靠近相关控件，以小号问号显示，悬停或聚焦时展示具体说明；正常界面保持简洁。
9. **交互避免冲突**：对话发送、生成计划书、生成邮件、上传资料期间互相禁用冲突按钮，避免同一时间重复触发。
10. **页面视觉方向**：统一调整整体页面和后续邮件页的布局、字体、字号、间距、颜色和卡片层次，使用偏自然、简洁并带科技感的视觉方向。
11. **书签式页面导航**：在同一长页面内按“咨询、计划书、邮件”移动，附前后导航按钮；生成结果后再开放对应页面入口。
12. **前台语言**：员工页面可见内容必须为日语；本文是团队内部说明，因此使用中文。

## 3. 当前网页实际怎么工作

当前模板是 templates/plan_compare.html，加载 static/app.css、static/workspace-theme.css 和 static/workspace.js。当前推进式工作区主要由 workspace.js 驱动。仓库里还保留 static/app.js 和若干旧接口；不要因为它们仍存在，就认为它们都在当前员工页面里执行。

### 3.1 项目选择与资料展示

- 页面启动时请求 /api/projects，服务端读取项目目录和 Markdown 文件。
- 当前数据目录只有 planty 一项，显示项目名称、已从资料提取的条件和关联资料。
- 项目条件字段包括项目名、出发地、目的地、预算、期限、客户到达期限、目的、出发时间、到达期限、返程期限、人数和住宿。
- 未输入或未确认的资料不会被项目字段提取器作为明确字段返回。
- 项目资料标题由目录指定；前端在显示文件名称时去掉路径和末尾扩展名。
- 关联文件可展开查看原文片段。
- 当前没有管理员网页去新增、编辑、审核或停用项目；维护人员要编辑 JSON 和 Markdown 文件。

### 3.2 对话和文件上传

- 页面把用户消息、最近会话、选择项目的字段、项目资料和本次上传资料送给 /api/agent/chat。
- 当前浏览器最多把最近 12 条对话传给聊天接口；服务端进一步使用最近 8 条作为模型聊天历史，意图评分使用最近最多 4 条历史内容。
- 上传的文件大小最多 25 MiB；支持 Markdown、PDF、DOCX、PNG、JPG/JPEG、TIFF、BMP、WebP；单个项目 Markdown 文件上限 1 MB。
- 上传后，页面显示资料标题、抽取文本块数和必要的部分识别提示；项目文件显示名称时隐藏扩展名。
- 上传资料进入当前工作区的资料库，聊天检索只允许选择项目关联文件和本次上传且已登记的文件。
- 页面将单个上传文本预览放进本地工作状态；项目资料、上传预览及聊天上下文有 12,000 字符上限，长资料送模型时会被截断。资料向量索引本身按全文分块建立。
- 读取失败、OCR 不完整时，页面能显示错误或提醒；部分抽取的文件不会进入当前 Agent 可用资料列表。
- 已实现资料删除接口，删除时移除绑定、向量集合和快照目录；页面会弹出确认。
- 当前对话主要提供说明、资料问答和条件补充。Agent 不会真的调用铁路或住宿 API，也不会预订或联系客户。

### 3.3 计划书生成

- 点击计划书按钮后，前端将尚未发送的输入框内容先作为一条用户补充信息，再调用本地规则解析接口 /api/intent/extract。
- 解析结果只覆盖代码列出的差旅字段；然后页面向 /api/simulation/offers 请求本地生成的模拟候选。
- 计划书由浏览器中的 buildProposal 组合为 Markdown，再在当前页面渲染；下载格式为 Markdown 文件。
- 计划书内容包括项目概况、登记资料中的差旅制度摘录、两套模拟候选、预算比较和“数据为模拟、实际班次及预约未确认”等说明。
- 计划书后会追加追问区。追问包含当前缺失字段，以及预算范围、本店所在地基点和适用制度等固定问题；回答后需要再次生成计划书才反映到新版本。
- 本次实现并不是从完整对话自动写回所有结构化字段。计划书字段主要来自项目 Markdown 与用户消息中的规则解析。
- 上传文件进入对话检索和 `/api/run` 的当前资料范围；计划书正文不重新展示上传资料清单，员工通过上传状态和会话核对原文，并明确补充条件。
- 切换项目时前端会清理聊天消息、追问、计划书和本次上传资料引用；需要新项目使用资料时，必须重新上传。
- 本地条件抽取请求失败时，计划生成会停止并提示重试，不会静默沿用项目旧字段。
- 计划书页面现在调用 /api/run；请求只包含当前项目文档和当前会话上传资料的 document_id、snapshot_id。服务端只在这一组资料中检索 `policy` 类型制度文档，防止把其他会话上传资料混入当前计划。模拟报价仍由页面读取，计划书仍由前端汇总；完整统一的服务端生成链路尚未完成。

### 3.4 当前模拟场景的默认值

`simulationScenario` 仍保留示例默认值的防御代码，但计划生成前会要求出发地、目的地、目的、出发时间、到达期限、返程期限、有效人数和住宿选择全部有值，因此缺失字段不会进入模拟请求。生成前的确认框会展示项目登记字段和本次会话内容，员工可取消并返回修改。若模拟接口出错，计划书会注明未能生成报价，不把系统默认值作为出行条件。

此前的默认示例输入包括：

- 出发日期：日本时间的次日。
- 出发时刻：08:00。
- 到达时刻：项目的客户到达期限若包含可识别时刻则使用该时刻，否则使用当日 12:00。
- 返程期限：同日 20:00。
- 人数：1 人。
- 住宿：未填写时按“不住宿”处理。
- 目的：未填写时用“确认出差条件”的示例文字。
- 发送给模拟接口的 TripRequest 被设为 confirmed=true，以便通过后端完整性检查。

以上示例默认分支目前仍在 `simulationScenario` 内，但必填条件门禁会在调用它之前拦截缺失值。仍需通过项目测试和页面操作验证所有边界输入均能触发门禁；在验证完成前不能称为最终可靠。

### 3.5 邮件页面

- 邮件按钮打开页面的邮件区，员工可填写收件对象和邮件目的。
- 当前邮件生成 API 是 /api/email/generate；发送至模型的字段包括项目名、收件对象、目的、项目资料、计划书和最近对话。
- agents/email_writer.py 固定使用 orcarouter/free，不按 A/B/C/D 改用付费模型。
- OrcaRouter 密钥未配置、模型依赖缺失、请求失败或回应格式错误时，会返回人工填写模板；界面提示邮件生成功能正在维护。
- 成功生成或模板返回后，员工可编辑件名和正文，并复制到剪贴板。
- 当前页面不发送邮件。邮件正文不会由当前邮件页面自动保存到邮件系统。
- 旧的 /api/draft 和 /api/draft/export 接口会调用 core.emailer 保存 JSON/EML 草稿，但当前 workspace.js 没有调用这些接口；不要把旧接口存在误认为当前邮件页已支持邮件系统或邮件发送。

### 4.2 服务端工作流和当前网页之间的差异

后端 core/planner.py 定义了受约束的工作流：先验证输入条件，再取规程证据，之后才对报价计算，并将结果写入 output/runs。core/calculator.py 检查完整性和行程约束。它不假装自己是能任意操作外部系统的 ReAct Agent。

当前网页的生成按钮先通过本地模拟接口取报价，再调用后端工作流执行行程、费用和规程检查，最后由浏览器拼装计划书。因此：

- 后端检查结果会列入员工计划书；行程案正文仍由浏览器根据模拟报价独立拼装，尚未完全改为同一结构化结果驱动。
- 后端计算器会把有效期未知、预约可用性未知、必填费用未知的模拟计划标成不完整，也不会将合规判定设为通过。
- 当前页面可以为了演示显示模拟小计和预算差额；这不等于后端已通过正式报价比较，也不等于预算或制度合规。
- 下一步应让计划书页面以 `/api/run` 的结构化结果为唯一展示来源，并保留模拟报价不可排名的阻塞说明。

## 5. Agent 和 OrcaRouter 具体运行方式

### 5.1 对话请求

当前对话 Agent 位于 agents/rag_agent.py：

1. 检查用户消息长度及 project_id。
2. 读取复杂度配置并计算 A/B/C/D 档位。
3. 检查 ORCAROUTER_API_KEY 与 LlamaIndex 是否配置。
4. 请求 OrcaRouter 总结用户意图和未提供的事实。
5. 按项目文档绑定范围及本次上传文件 ID 限定检索范围。
6. 从本地资料库搜索最多 6 条相关文本片段。
7. 把用户问题、最多 8 条聊天历史、项目资料、检索片段交给 LlamaIndex 的上下文聊天引擎和模型生成回答。
8. 对回答中出现的引用编号做存在性检查，返回回答和引用资料。
9. 后端响应移除模型路由、复杂度诊断等内部字段；前台用户只看到回答和可展开的资料依据。

一次对话最多可能产生两次模型请求：一次意图总结、一次依据回答。资料搜索和字段计算由本地执行，不由模型负责。模型只可使用已有检索资料回答制度问题；没有真实交通数据时，提示约束禁止编造班次、价格和预约状态。

失败状态包括没有模型配置、依赖缺失、没有资料、没有检索到依据、资料检索错误、模型错误等。检索不到证据时不会声称制度中不存在相应规则。

### 5.2 复杂度公式与路由

实现位于 agents/intent_router.py，配置位于 config/llm_tiers.json。

总分为以下五项的加权和，最终四舍五入到整数：

- 输入长度 × 0.20：当前消息加最近最多 4 条历史消息；2,000 字符达到 100 分。
- 已填写差旅字段长度 × 0.20：8 个识别字段中的非空值总字符数；800 字符达到 100 分。
- 字段覆盖率 × 0.15：8 个字段中非空字段占比。
- 词汇复杂度启发值 × 0.20：不同词元占比乘 60，加长度至少 6 字符的词元占比乘 40。
- 条件表达数量 × 0.25：代码词表命中的中文、日文、英文条件词，以及日期和时刻表达；7 个命中达到 100 分。

| 档位 | 分数区间 | 评分请求路由 | 默认实际路由 |
| --- | ---: | --- | --- |
| A | 76–100 | orcarouter/fusion | orcarouter/free；付费路由须显式允许 |
| B | 51–75 | orcarouter/fusion-mini | orcarouter/free；付费路由须显式允许 |
| C | 26–50 | orcarouter/auto | orcarouter/free；自动路由须显式允许 |
| D | 0–25 | orcarouter/free | orcarouter/free |

这是文本启发式评分，不是经对照实验验证的“模型能力等级”。短消息中的否定、模糊指代、信息相互矛盾等语义难点，不能由字符数和关键词命中充分表达。当前评分还会计入助手历史内容，因此较长的历史可能抬高等级。

此前使用用户给出的密钥请求模型目录，返回 HTTP 200 和 198 个模型；向 deepseek/deepseek-v4-flash-free 发起生成请求，返回 HTTP 429、err_free_access_denied，没有模型回答。此前没有调用收费模型。密钥没有写入项目源码或项目文档。当前 `llm/orcarouter.py` 默认将复杂度分流的实际请求限制为 `orcarouter/free`，只有明确设置 `ORCAROUTER_ALLOW_PAID=true` 才允许 A/B/C 的配置路由；免费路由被拒绝时不会自动切换到收费模型，而是走规则解析或维护模板。

### 5.3 内部运行记录

agents/trace_log.py 将阶段、档位、分数、特征、数据类型、来源、引用数、检索方式和已识别错误码写入 output/agent-traces/agent-trace.jsonl。记录中不写入完整提示词、API Key、聊天正文、资料原文、收件对象或完整差旅字段。

前台不展示模型档位和路由信息。追踪按单次 HTTP 请求生成 ID，不会跨多个请求自动汇总为一名用户的完整会话。日志写入失败不阻塞员工操作。

注意：运行追踪、`output/runs` 和 `output/drafts` 均已被 `.gitignore` 排除；这不能清除可能存在的历史提交内容。

## 6. 文件导入、OCR、索引和资料检索细节

### 6.1 支持格式及限制

员工上传接口接受 Markdown、PDF、DOCX、PNG、JPG/JPEG、TIFF、BMP、WebP；单文件最多 25 MiB。员工网页上传不接受 HTML。内部抽取模块可以处理 HTML，但要求调用方明确指定 CSS 选择器，不会猜测抓取网页正文区域。

其他限制：

- PDF 最多 200 页。
- 单张图像或 PDF 页面进行 OCR 时，像素上限为 50,000,000。
- 项目目录内供项目选择器读取的 Markdown 文件最多 1 MB。
- 图片 OCR 使用本地 RapidOCR，并针对日文、中文和拉丁文字配置模型。
- PDF 先提取文本和表格；扫描页或文字稀疏且含图片的页面会尝试 OCR。
- OCR 置信度低于代码阈值时记录低置信度提醒。识别到错误或内容不完整时，系统不能保证法律、财务或规程数值准确，应对照原文件。
- PDF 表格会保留表格网格、单元格和页面位置；规程章节、条款和附表会用于分块。
- 文档、页码、方框位置、条款标记、引用关系和抽取问题保存在快照数据中。

### 6.2 版本快照和语义索引

- 文件内容用 SHA-256 计算摘要；资料快照由资料规格、文件摘要和解析器版本共同标识。
- 已存在的同一快照会复用，避免重复导入。
- 原文件、抽取区块和快照记录写入 data/policies/snapshots。
- 每份资料有 document_id 与 snapshot_id；Binding 将公司范围、用途范围和资料版本绑定起来。
- 生产用途绑定要求 company_id 和审批依据；模板资料不能绑定到生产用途。
- Demo 当前使用 company_id=null、usage_mode=demo；不是实际公司的多租户授权系统。
- 向量模型为 multilingual MiniLM L12 v2 的 384 维 FastEmbed；向量由本地模型生成并存到 Chroma 持久目录 storage/chroma。
- 搜索会校验请求中的文档 ID 与快照 ID 是否精确对应绑定范围；按语义距离取前 N 条，并沿已解析引用关系带回相关条款或附表。
- 每个资料快照单独建集合。模型或索引元数据不一致时会重建索引。
- 首次使用 FastEmbed 需要下载约 220 MB 模型；模型缓存在 models 目录，云部署需要持久磁盘。
- 部分抽取文件不进入 Agent 的可用来源列表，避免把不完整文本作为完整依据。

### 6.3 当前资料检索的边界

- 语义搜索未命中只表示没有找到相关片段，不代表制度里没有该条文。
- 模型只检查其回答是否使用了合法引用编号；代码没有逐句验证每个结论是否真正被引用原文支持。
- 旅费规则接口返回 evidence、引用与需人工复核状态；对检索到且原文明确写出的住宿上限和超额住宿审批条款提供带位置与正文哈希的 `rules`，compliant 与 needs_approval 仍保持 null。
- 图片 OCR、PDF 表格解析和文档抽取虽然有实现，但没有在本次任务执行自动化回归测试，也没有针对全部资料格式逐一做人工视觉复核。
- 项目登记资料会在 GET /api/projects 请求过程中逐项 ingest 并 bind。相同内容具有幂等快照，但项目读取接口同时承担了初始化资料库的写入工作，首次加载可能涉及模型下载和向量索引构建。

## 7. 规则解析、数据结构、计算和排序

### 7.1 项目资料字段提取

project_catalog.py 从 data/projects/catalog.json 读取项目 ID、名称和 Markdown 文件路径。项目 ID 只允许小写英文字母、数字和连字符；项目文件路径必须解析到 data/projects 子目录内；扩展名必须是 .md。

字段只从格式精确的 Markdown 列表读取，形式为“- 日文标签：值”。字段标签和结构字段精确对应，包含出发地、目的地、预算、期限、到达期限、目的、日期、人数和住宿。金额仅按“数字＋円”转换为整数，期间仅按“数字＋日以内”解析，人数仅按“数字＋名”解析，住宿仅将“必要/不要”转换为布尔值。

这不是任意 Markdown 的通用理解器；新增项目需遵循对应格式。catalog.json 当前只登记 planty 两份资料。

### 7.2 自然语言差旅字段解析

core/intent_parser.py 和 /api/intent/extract 负责本地规则抽取，意图字段包括：

- 出发地和目的地：识别部分“从某地点出发前往某地点”、箭头和中文“从/到”等格式。
- 日期：支持 ISO 或年月日形式、今天/明天/后天及带时区基准时间的“下周星期几”。
- 时间：支持 08:30、8時半、8時30分形式；到达截止时刻只识别有限表达。
- 人数：匹配数字加人或名。
- 目的：从预设的客户访问、会议、研修等词中提取短语。
- 住宿：出现酒店、住宿、过夜、一晚等关键词就记为需要住宿；出现日归才记为无需住宿。
- 缺失字段：地点、出发时刻、客户到达时间、返程时刻、目的、人数、住宿会被要求补充。
- 相对日期必须有带时区的基准时间；没有基准时间时，不自行把“明天”等换成绝对日期。
- TripRequest 时间必须带时区；出发、到达、返程的时间顺序有 Pydantic 校验。

解析器并不是完整的自然语言理解模型。本轮已让明确的中文、日文住宿否定词优先于住宿关键词，但否定表达仍受词表覆盖范围限制；单条消息中的多个时间也可能按出现次序被简单解释。多日出差表达不会自行猜返程日期。未抽取的条件会要求员工明确补充。

### 7.3 费用计算和后端比较

core/calculator.py 是确定性代码，不把费用乘法交给 LLM。它会：

- 按单价与数量计算已知金额，汇总类别和已知小计。
- 检查是否有交通费、当地移动费、日当；需要住宿时还检查住宿费。
- 对零金额类别要求提供明确的 zero_cost_reasons，不能静默省略。
- 单价、数量或税费是否含税未知时，把总额标为不完整。
- 检查往返路线是否齐全、出发地和目的地是否匹配、换乘区间是否衔接、时间是否重叠、是否超过到达或返程期限。
- 检查报价有效期、预约可用性；有效期未知、过期或可用性未确认均不会进入有效比较名单。
- 永远不因费用算术成功就断言规程合规；compliant 与 needs_approval 维持未判定。
- /api/plans 禁止混合 real 和 simulation 类型的报价进行同一排名。
- 后端排名只使用费用完整、行程合规、可用性为 true 且报价仍有效的记录。

当前模拟报价的 valid_until=null、available=null，且日当未定，因此经后端 Calculator 会被标为不完整，也不会成为有效价格排名候选。当前页面通过浏览器直接展示模拟小计，没有使用此后端排名结果。

## 8. 模拟数据算法：明确什么是真实、什么是假设

实现位于 tools/simulation_provider.py。接口只构造本地数据，不会请求铁路、酒店或座位库存服务。结果的 data_kind 为 simulation，available 与 valid_until 均未知。

### 8.1 交通候选

当前每次生成两套对照候选：

| 项目 | 速达方案 | 费用重视方案 |
| --- | ---: | ---: |
| 模拟单程时间 | 147 分钟 | 180 分钟 |
| 模拟时刻偏移 | 基准出发时刻 | 比第一方案晚 10 分钟 |
| 东京—大阪单程金额 | 14,720 日元参考基准 | 14,400 日元人为设定的对照数 |
| 其他区间单程占位金额 | 12,000 日元 | 10,800 日元 |
| 每人当地交通占位金额 | 1,200 日元 | 900 日元 |

- 往返交通费用按单程金额 × 人数 × 2 计算。
- 东京—大阪匹配由地点字符串包含东京/Tokyo 与大阪/新大阪/Osaka 判断。
- 第一档 14,720 日元取自公开页面的参考金额，但代码不是对该页面或铁路服务发起实时请求，因此仍不是本次出行的报价。
- 第二档 14,400 日元比第一档少 320 日元，是人为设定的比较值，不代表实际折扣。
- 去程到达时刻按模拟出发时刻加上 147 或 180 分钟生成。
- 返程出发时间按“返程截止时间减单程时长”与“到达后等待至少 30 分钟”两者取较晚时间；如果因此超过返程期限，后端行程检查应判为不合格。
- 路线名称使用两种速达类别标签，仅表示演示类别，不代表具体车次或运营时间表。

### 8.2 住宿和未确认费用

- 只有场景认为需要住宿时才生成模拟酒店；系统使用目的地站附近的虚构名称和虚构地址描述。
- 当前每晚模拟价为 9,800 日元和 12,000 日元；假定一间房；晚数按返程日期减出发日期计算，至少一晚。
- 酒店位置、名称、空房、步行时间和预约能力都不是真实信息；当前 walking_minutes 为 null。
- 日当单价、计费人数或日数不从用户截图推断，费用项保留空值。
- 座位库存值为 null，页面仅说明余席未确认，没有生成模拟余席数量。
- 模拟报价把可用性设为 null，把有效期设为 null，因此不是可购买报价。

### 8.3 发现的文档不一致

docs/ORCAROUTER_AGENT_INTERNAL.md 记载过 13,800/10,800 日元酒店价、8/14 席模拟库存和 8/12 分钟步行距离；当前 tools/simulation_provider.py 实际生成的是 9,800/12,000 日元酒店价、座位库存为空、步行距离为空。当前代码是运行时实际行为，内部说明文档需要同步修正。路演时必须讲当前代码值，不要照搬旧文档数字。

## 9. 邮件功能的实现级别和数据流

### 当前工作区里的邮件生成

- 员工输入收件对象和邮件目的；邮件上下文还包括项目资料、已有计划书和最近最多 10 条对话，并受输入字段长度限制。
- 服务端 agents/email_writer.py 只选择 orcarouter/free。
- 请求提示要求模型只返回 subject/body JSON，不编造未提供的时间、金额、预约情况，不把模拟数据当真实信息，不执行邮件发送。
- 回答 JSON 会校验字段类型，并把件名限制到 300 字、正文限制到 12,000 字。
- 没有 Key、依赖不可用、网络/API 报错、免费权限拒绝或响应格式错误时返回固定日语模板。
- 生成结果可在网页上编辑和复制；没有真实邮件账号、发送 API、收件人目录或发送动作。
- 收件对象及项目、计划、对话内容在配置 OrcaRouter 时会随生成请求发送给模型服务。后端追踪不会保存这些字段，但这不等于第三方模型服务没有处理这些内容；上线前需确认服务方数据处理条款并减少不必要的个人信息。

### 旧的邮件导出流程

core/emailer.py 的 /api/draft 可以从 PlanInput 生成明确标记为未发送的邮件文本；/api/draft/export 会将含收件地址的 JSON 与 EML 文件存到 output/drafts 并提供下载链接。当前推进式页面不调用该流程。当前模板邮件页面也不调用邮件发送适配器 tools/email_api.py；该适配器只返回 not_configured。

## 10. 安全、隐私和运行部署

### 已有保护

- 本地服务默认监听 127.0.0.1；监听公网地址必须设置 APP_ACCESS_PASSWORD，并配置精确的可信主机名。
- 公网请求限制在 APP_TRUSTED_HOSTS 或 RENDER_EXTERNAL_HOSTNAME；非本机请求会检查主机、HTTPS 来源和访问码。
- 访问码通过常量时间比较校验；前端成功后把 bearer token 暂存于当前浏览器 sessionStorage。
- 资料接口按 demo binding、document_id 和 snapshot_id 做范围校验；路径解析限制项目文件留在 data/projects 内。
- 上传文件大小、类型、PDF 格式、项目文件大小、图像像素数均有检查。
- 返回响应设置 no-store、nosniff、X-Frame-Options、Cross-Origin-Opener-Policy、no-referrer 和内容安全策略；HTTP 访问日志不记录正文和邮件收件人。
- 前端大多用 textContent 建立元素，避免把模型或文件原文作为 HTML 执行。
- OCR 与向量嵌入在本地处理；但启用模型后，对话、相关资料片段和邮件上下文会发送到 OrcaRouter。

### 当前安全缺口和配置差异

1. **Git 历史清理仍需确认**：`.gitignore` 已排除 output/agent-traces、output/runs、output/drafts、运行快照、绑定文件和向量库；如果远端历史曾跟踪运行记录或邮件草稿，仍需单独清理历史。
2. **部署文档与忽略规则不一致**：本轮已让 `.dockerignore` 只排除运行期 `data/policies`，保留 `data/projects`；`.gitignore` 排除运行期快照、向量库、绑定文件和输出目录。提交前仍需检查仓库历史。

## 13. 当前问题按优先级排序

### P0：会影响计划正确性或数据保护的问题

1. **模拟默认值曾被作为已确认输入**：本轮已增加必填条件门禁，并在模拟报价前要求员工确认登记字段和会话内容；抽取失败时停止。备用处理是补充条件、重试或取消，不生成计划。仍需测试验证，详见 docs/FINALIZATION_TRACKER.md。
2. **计划书展示仍有双重数据组装**：本轮已接入 `/api/run` 并限定文档范围；行程案正文仍由前端直接读取模拟报价生成。备用处理是在后端不可用时显示带明确标记的模拟草稿，并指出后端检查未完成。
3. **上传资料不会自动变成已确认条件**：计划书会列出本轮资料并将其纳入后端检索范围，但不会把 OCR 或预览内容直接写成出差字段。员工需要通过会话确认；无法确认时保留人工补充降级路径。
4. **切换项目时上传资料状态可能残留**：本轮已在项目切换时清空当前上传引用，并让上传 ID 同时绑定文件名与内容摘要；需通过跨项目页面验证复核。
5. **Git 运行产物忽略规则不完整**：本轮已忽略 output/runs 和 output/drafts；当前工作区没有提交历史，无法据此证明其他克隆或远程历史从未收录过运行数据。
6. **模型档位可能触发付费路由**：A/B/C 配置仍存在；本轮已增加默认免费闸门，只有 `ORCAROUTER_ALLOW_PAID=true` 才会实际启用这些路由，仍需组织授权和付费路由验证。
7. **私有资料会发给模型服务**：对话会把用户消息、上下文和检索片段交给 OrcaRouter；邮件生成也会传收件人和业务上下文。需确认服务处理条件并取得组织授权。
8. **当前页面状态与旧内部文档不一致**：模拟住宿金额、座位库存、步行时间记录已过期；应以当前代码为准，并修正文档。

### P1：会降低业务可靠性的问题

- 自然语言解析器对“不要住宿”等否定、多个时间、日期范围、返程表达的处理有限。
- 当前追问有一部分是前端硬编码的固定问题，不是 Agent 根据资料和风险动态排序的问题。
- OrcaRouter 一次聊天可能两次调用，额外增加延迟、失败点和潜在费用。
- 复杂度评分是可复现启发式，没有通过中日文业务语料校准，也没有与模型质量进行基准测试。
- 引用编号检查不等于逐句证据验证；回答仍需要原文审核。
- 项目文件的登记只能改 JSON/Markdown，没有管理员审批、项目生命周期和组织权限。
- 资料和向量库本地持久化，没有正式备份、删除期限、加密或跨多实例方案。
- /api/projects 在读取项目时会同时初始化资料索引，首次访问延迟可能较长。
- Render 部署文档的费用和配置可能变动，当前没有线上部署证据。
- 旧版 /api/plans、/api/run、/api/draft 等接口与当前页面存在代码重复，需要确定保留、接入或淘汰。

## 15. 最后：五个维度接下来分别优化什么

### 15.1 安全

**当前短板**

- 输出运行记录和邮件草稿可能被 Git 跟踪；远端已有历史文件。
- 团队共用一个访问码，没有逐人权限与操作审计。
- 对话、资料片段及邮件收件人会发送到 OrcaRouter。
- 曾在聊天中提供过 OrcaRouter 密钥；代码没有保存，但仍需确认密钥状态。
- 上传资料没有自动到期删除、加密存储和组织级保留规则。

**具体优化**

1. 检查并清理 output/runs、output/drafts 中可能含业务资料的文件；设置 Git 忽略并决定是否要清理历史。
2. 确认此前提供的 OrcaRouter 密钥已撤销或轮换；新密钥只放服务端秘密管理环境。
3. 明确发送给 OrcaRouter 的字段，邮件只发送生成必要信息；确认服务的数据保留和训练使用政策。
4. 为员工接入个人身份和角色权限；按公司、部门和项目做资料隔离。
5. 增加上传资料保留期限、删除确认、备份和访问记录。
6. 部署前检查 HTTPS、主机白名单、访问码、频率限制和错误日志。

**路演证据**

展示密钥不在浏览器、访问未授权被拒绝、跨项目资料不能串用、邮件只生成草稿、上传文件可删除，以及模型请求字段经过最小化。

### 15.2 成本效益

**当前短板**

- 交通和酒店方案是模拟值，不能证明真实出行成本。
- D 免费路由曾不可用；A/B/C 路由没有费用或质量验证。
- 当前对话可能一次调用模型两次。
- 没有量化原人工流程耗时、模型费用和节省工时。
- 预算比较使用已知模拟小计，不等于总费用，日当等项目仍未确定。

**具体优化**

1. 在预算保护下只验证免费路由；默认锁定免费模型，禁止评分自动切到付费和自动路由。
2. 评估能提供指定日期路线的铁路服务与实时住宿服务，先核对免费额度、付费规则、字段和使用条款。
3. 将交通、酒店、地面移动、日当拆成可说明来源和数量的成本项；未知金额不填零。
4. 记录模型调用次数、路由、耗时、错误码和估算成本，不记录正文及密钥。
5. 与人工办理流程做至少一组同条件对照，记录资料阅读、询问和文书时间变化。

**路演证据**

同一出差条件下展示真实 API 返回的来源、查询时间和费用构成；用未经确认的空项展示“未形成完整总价”；展示人工流程与 Agent 流程的计时结果。

### 15.3 可靠性与健壮性

**当前短板**

- 计划书流程会使用未确认的默认条件并标记已确认。
- 计划书仍由前端独立组装正文，尚未完全由后端结构化工作流结果驱动。
- “不要住宿”、多时刻和日期范围等输入可能被规则误判。
- 资料引用通过编号存在性检查，未逐句核实语义支持。
- 内部文档的模拟酒店和库存数据与当前代码不一致。
- 本轮已使用 `.venv` 运行 `unittest discover -s tests -v`，55/55 项通过。测试依赖的公开 PDF 按 `config/import_jrfu.json` 下载并保存在被忽略的本地资料目录；这不等于线上部署已验证。

**具体优化**

### 15.4 自主性

**当前短板**

- 当前 Agent 是资料问答和模型摘要，不会自主调用已接入的真实交通或住宿工具。
- 邮件、计划书和对话之间的字段状态没有统一的确认与同步模型。
- 追问部分由固定问题列表生成，不会完全根据缺失字段严重程度调整。
- 计划书只读取项目字段和用户文本解析，没有保证吸收上传文件内容。
- 模型输出没有在全部场景下成功运行验证。

**具体优化**

1. 先把项目资料、上传文件、聊天确认字段和法规证据整理成统一状态对象，并逐字段保留来源、是否确认和更新时间。
2. 让 Agent 根据缺失字段和业务影响排序追问；用户每次答复后更新状态并展示变更。
3. 获得授权并配置真实服务后，由工具适配器按规则查询铁路与住宿数据；每个工具都返回来源、查询时间和结构化失败状态。
4. 由独立的确定性检查器检查 Agent 结果；模型不能自行判定预算合规、审批通过或预约成功。
5. OrcaRouter 生成成功后再验证模型回答；模型不可用时保持规则解析与维护模板，不声称 AI 已完成。
6. 保留人工确认节点：员工确认条件、选择方案、提交审批或发送邮件。

**路演证据**

从选择 planty 和上传资料开始，展示系统识别信息来源、发现空项、逐轮询问、调用真实查询、检查返回、生成计划和邮件草稿；最后展示员工确认点，并证明没有自动订票或发送。

### 15.5 创意与独创性

**当前短板**

- 单页流程和资料／规程融合是产品方向，尚无真实公司部署数据证明价值。
- 当前模拟路线和酒店数据不能证明业务可执行。
- 计划书与后端规程计算链路尚未真正合并。
- 五个维度的材料还需要用现场可核验证据支撑，不能只讲概念。

**具体优化**

1. 把差旅规程的条款、例外理由、路线来源、费用项目、审批事项连接成逐项可追溯的计划记录。
2. 让计划书分别标出“来自项目资料”“员工确认”“外部 API”“系统模拟”“待核实”，而不是只给出总答案。
3. 展示差旅项目专属背景如何帮助生成业务目的和客户问题，同时明确区分公开项目事实与虚构的 planty 设定。
4. 选择一个真实、去敏的业务案例，让员工参与试用；测量节省的时间、遗漏条件、规程问题发现率和草稿修改量。
5. 准备正常、预算冲突、条件不足、规程例外、服务故障五种演示流程，用系统证据展示每一种处理结果。

**路演证据**

把“项目资料 + 公司规则 + 真实查询 + 明确追问 + 可追溯计划书 + 人工确认”演示成一条完整业务链，并用试用数据说明它比人工收集信息和整理邮件减少了哪些工作。
